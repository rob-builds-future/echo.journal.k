## Notes

- The inventory treats `SettingDetailScreen` as one screen with multiple internal setting variants, because navigation is route-based on `setting/{type}` and the variant content is composed inside that host.
- The onboarding substeps are not separate navigation destinations in the current code; they are local-state steps inside `OnboardingFlow`.
- No standalone routed screen was found for notifications. `ProfileSettingNotifications.kt` exists as a component-level file in the manifest, but it is not wired into `SettingDetailScreen` or the current `SettingType` switch, so it is excluded as a screen.
